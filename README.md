# Claude Code Harness

Настройка для [Claude Code](https://claude.ai/code), которая превращает одну сессию
в небольшую команду. Главная сессия ставит задачу, планирует и принимает результат,
а исследование, код и ревью делают узкие агенты. Каждый коммит проверяют несколько
ревьюеров, судья сверяет их находки с кодом, исправления коммитятся сами, пока ревью
не станет чистым. Хуки не дают случайно испортить основное рабочее дерево.

## Почему это удобно

- **Ревью каждого коммита без ручной работы.** `/review` параллельно запускает
  ревьюеров: логика, безопасность, чистота кода, производительность, архитектура,
  документация, сверка с планом. Судья проверяет каждую находку по коду и отбрасывает
  ложные, исполнитель чинит подтверждённое, затем ревью повторяется. Вам приходит
  короткий итог: чисто или что осталось решить.
- **Ошибки ловятся до кода.** Для крупной задачи пишется план. Два ревьюера сверяют
  его с кодом и с правилами проекта, потом главная сессия проверяет его сама и только
  после этого показывает вам. Нерешённые развилки приходят вопросом с вариантами,
  а не решаются молча.
- **Главная сессия не раздувается.** Каждый её ход заново отправляет весь накопленный
  контекст, поэтому чтение кода, поиск и длинные логи уходят агентам. Агент пишет
  результат в файл и возвращает несколько строк выводов. Циклы ревью и планирования
  ведут агенты-распорядители, главная сессия видит только статус. Сессия живёт дольше
  и стоит дешевле.
- **Взгляд на ветку целиком.** Один раз за задачу «свежий читатель» без плана читает
  итог всей ветки и ищет код, который обещает больше, чем делает: метод без боевого
  вызова, имя или описание, разошедшееся с поведением, член, нужный только тестам.
- **Основное дерево под защитой.** Все правки идут в git worktree. Один хук отказывает
  в записи отслеживаемых файлов основного дерева, второй — в `checkout`, `switch`,
  `reset --hard` и `branch -f` там же. Это снижает риск потерять чужую незакоммиченную работу; хуки ловят
  случайные ошибки, а не сознательный обход через shell. У обоих хуков есть тесты.
- **Техдолг не теряется.** Что нельзя чинить сейчас, сразу записывается в
  `docs/tech-debt/` с номером. В конце задачи `/finalize` закрывает долги именно этой
  сессии: очевидное чинит сам, спорное спрашивает.
- **Память между сессиями.** Каждый коммит попадает в журнал вместе с id сессии: по
  хэшу можно вернуться в ту сессию через `claude --resume`. Отложенные идеи пишутся
  в журнал и переживают сжатие контекста. Агенты сообщают о сбоях самого процесса
  в отдельный журнал. Сбои процесса и отложенные идеи разбирает `/finalize`.
- **Осторожные настройки по умолчанию.** Заранее разрешены git status/diff/log/show и несколько
  простых утилит (ls, grep, mkdir, sort, wc, jq); push и другие пишущие git-команды
  спрашивают подтверждение.

## Как идёт задача

```
задача
  -> классификация: ответ / мелкая правка / крупная задача
  -> исследование кода          research-writer, отчёт в файл
  -> варианты, вы выбираете
  -> план и его ревью           plan-runner: planner и две проверки
  -> вы одобряете план
  -> реализация в worktree      implementer
  -> /review после каждого коммита
  -> свежий читатель по ветке   /review scope=branch
  -> приёмка итогового diff главной сессией
  -> /finalize                  техдолг сессии, отложенные идеи
  -> merge или pull request     как велит CLAUDE.md проекта
```

Мелкая правка идёт коротким путём: правка в worktree, коммит, `/review`. Полный
порядок шагов и причины каждого — в `rules/workflow.md`.

Цикл ревью внутри выглядит так:

```
/review
  -> review-runner
       -> ревьюеры параллельно (набор зависит от того, что поменялось)
       -> review-judge        сверяет каждую находку с кодом
       -> implementer         исправляет подтверждённое
       -> fix-коммит
       -> повторное ревью, пока не станет чисто или не кончится прогресс
```

- `mode=full` (по умолчанию) — находки исправляются и коммитятся.
- `mode=analysis-only` — для чужого кода: без правок и коммитов, только вердикт.
- `scope=branch` — проход свежего читателя по всей ветке.
- `plan=<путь>` — добавляет сверку коммита с планом реализации.
- `/review-mr` — тот же цикл для merge request в GitLab через `glab`, в режиме
  `analysis-only`.

## Быстрый старт

Если `~/.claude` ещё нет, достаточно клонировать репозиторий и создать настройки:

```bash
git clone https://github.com/Forcharc/claude-config-shared.git ~/.claude
cp ~/.claude/settings.example.json ~/.claude/settings.json   # затем отредактируйте
```

Если `~/.claude` уже существует (Claude Code создаёт его при первом запуске), сначала
отодвиньте его. Вместе с ним в резервную копию уйдут учётные данные, сессии и
`projects/`: придётся войти заново, а история старых сессий останется в резервной копии.

```bash
mv ~/.claude ~/.claude-backup
git clone https://github.com/Forcharc/claude-config-shared.git ~/.claude

# Верните свои настройки и историю
cp ~/.claude-backup/settings.json ~/.claude/ 2>/dev/null
cp ~/.claude-backup/settings.local.json ~/.claude/ 2>/dev/null
cp ~/.claude-backup/history.jsonl ~/.claude/ 2>/dev/null
[ -f ~/.claude/settings.json ] || cp ~/.claude/settings.example.json ~/.claude/settings.json
```

После этого перезапустите Claude Code и поправьте `settings.json` под себя.

### Только цикл ревью

Если весь процесс не нужен, а нужен только `/review`, возьмите весь каталог `agents/`,
скиллы `review`, `agent-core-preamble`, `reviewer-findings-output`, `commit`, `techdebt`,
`techdebt-init` и правила `workflow.md`, `code-says-what-it-does.md`,
`repo-references.md`. На них цикл ссылается: `/commit` делает fix-коммиты, `/techdebt`
записывает подтверждённый судьёй долг, `docs-reviewer` проверяет тексты по
`repo-references.md`.

## Агенты

Все агенты лежат в `agents/`. Общие куски промптов подгружаются из библиотек
`agent-core-preamble` и `reviewer-findings-output` через поле `skills:` во frontmatter.

| Агент | Роль |
|-------|------|
| `review-runner` | Ведёт цикл ревью: выбирает ревьюеров, запускает их, зовёт судью, исправляет, ревьюит повторно |
| `review-judge` | Сверяет каждую находку ревьюера с кодом; подтверждает, откладывает как техдолг или отбрасывает |
| `logic-reviewer` | Баги, крайние случаи, обработка ошибок, гонки |
| `security-reviewer` | Секреты, чувствительные данные в логах, отсутствующие проверки, небезопасная обработка ввода |
| `clean-code-reviewer` | Лишний и мёртвый код, умозрительные абстракции, именование, дублирование |
| `efficiency-reviewer` | Лишняя работа, упущенная параллельность, утечки |
| `architecture-reviewer` | Слои, зависимости, публичный API, обратно несовместимые изменения |
| `docs-reviewer` | Документация, разошедшаяся с кодом, ссылки на то, чего читатель не увидит |
| `plan-compliance-reviewer` | Сверяет коммит с планом: что пропущено, что лишнее, где отступили |
| `fresh-reader-reviewer` | Читает итог всей ветки без плана и проверяет, что форма кода совпадает с поведением |
| `plan-runner` | Ведёт составление и ревью плана |
| `planner` | Пишет подробный план реализации в файл |
| `plan-factcheck-reviewer` | Сверяет утверждения плана с кодом и внешними источниками |
| `plan-standards-reviewer` | Сверяет план с правилами проекта и устоявшимися паттернами |
| `research-writer` | Исследует кодовую базу и пишет отчёт в файл |
| `implementer` | Пишет и правит код по плану или задаче, гоняет проверки проекта |

## Скиллы

Скиллы лежат в `skills/<name>/SKILL.md`.

| Скилл | Назначение |
|-------|------------|
| `/review` | Запускает цикл ревью |
| `/review-mr` | Ревьюит merge request в GitLab через `glab` |
| `/commit` | Оформляет коммит и запускает ревью; пушит, только если проект это разрешил |
| `/techdebt` | Записывает пункт техдолга с автоматическим номером |
| `/techdebt-init` | Создаёт структуру каталогов для техдолга |
| `/finalize` | Закрывает техдолг сессии, разбирает сбои процесса и отложенные идеи |
| `/fork-init` | Настраивает форкнутую сессию с собственным worktree |
| `/txt` | Записывает текст в файл и открывает его, чтобы было удобно скопировать |
| `agent-core-preamble` | Библиотека для агентов: чтение правил, проверка worktree, сообщения о сбоях процесса (подгружается агентами, напрямую не вызывается) |
| `reviewer-findings-output` | Библиотека для ревьюеров: как писать файл находок (подгружается ревьюерами, напрямую не вызывается) |

## Правила

Правила лежат в `rules/`. Первые три действуют в каждой сессии; последние два
включаются только для файлов из поля `paths:` во frontmatter.

| Файл | Содержание |
|------|------------|
| `workflow.md` | Весь рабочий процесс: оркестрация через агентов, worktree, кому что делегировать |
| `protocol.md` | Как ассистент общается: нумерованные пункты, варианты с рекомендуемым, цитаты |
| `repo-references.md` | На что можно и нельзя ссылаться в текстах, которые попадают в репозиторий |
| `code-says-what-it-does.md` | Форма кода должна соответствовать боевому поведению; в боевом коде нет членов только для тестов |
| `check-dependency-versions.md` | Перед добавлением или обновлением зависимости проверить актуальную версию |

## Хуки и строка статуса

| Файл | Назначение |
|------|------------|
| `hooks/worktree-boundary.sh` | `PreToolUse` на Write/Edit/MultiEdit/NotebookEdit: отказывает в записи в основное рабочее дерево git-репозитория (кроме файлов, игнорируемых git, и живых конфликтов слияния) |
| `hooks/git-branch-guard.py` | `PreToolUse` на Bash: отказывает в `git checkout`, `switch`, `reset --hard` и `branch -f` в основном рабочем дереве |
| `hooks/*.test.sh` | Тесты обоих хуков |
| `statusline.sh` | Строка статуса: папка, модель, заполненность контекста, стоимость за месяц |

Хуки ловят случайные ошибки, а не сознательный обход через shell: правило остаётся
правилом, хук его страхует.

## Требования

- Claude Code
- git и bash
- `python3` (хук `git-branch-guard.py`)
- `jq` (`statusline.sh` и `skills/review/runner-wait.sh` — без него они завершаются
  с ошибкой; `worktree-boundary.sh` без него пропускает свои проверки)
- `glab`, настроенный на ваш экземпляр GitLab (только для `/review-mr`)
- `ccusage`, запускаемый через `npx` (только для стоимости за месяц в строке статуса)
- macOS: `statusline.sh` вызывает `stat -f`, то есть BSD-форму. В Linux замените эти
  вызовы на `stat -c`.

## Файлы, создаваемые при работе

Эти файлы харнес пишет сам; в репозиторий они не входят.

- `projects/<slug>/memory/agent-results/` — отчёты, которыми обмениваются агенты
- `projects/<slug>/memory/flow-feedback.md` — сбои, с которыми агенты столкнулись в самом процессе
- `projects/<slug>/memory/commit-sessions.md` — какая сессия сделала какой коммит
- `projects/<slug>/memory/session-threads.md` — идеи и вопросы, отложенные в ходе сессии
- `.tmp/` в ваших рабочих репозиториях — временные файлы и логи

`<slug>` — абсолютный путь к `~/.claude`, в котором каждый `/` и `.` заменён на `-`.

## Пример настроек

`settings.example.json` — минимальная отправная точка для `settings.json`:

- Два хука `PreToolUse`: `worktree-boundary.sh` для правок файлов и
  `git-branch-guard.py` для Bash.
- `statusLine` указывает на `statusline.sh`.
- `includeGitInstructions: false` отключает встроенные git-инструкции Claude Code;
  их заменяет git-раздел `CLAUDE.md`.
- `defaultMode: default` сохраняет обычные запросы разрешений. Заранее одобрены только
  git-команды, которые лишь читают (`status`, `diff`, `log`, `show`), и несколько
  безопасных утилит; добавьте команды, которым доверяете. Форма `git -C <path> ...`
  этими правилами не покрыта и тоже будет спрашивать; добавляйте `Bash(git -C:*)`
  только осознанно, потому что оно покрывает и `push`.

## Настройка под себя

- `CLAUDE.md` — шаблон без персоны и имени пользователя. Добавьте свои: как ассистенту
  обращаться к вам, соглашения ваших проектов.
- Язык ответов задаёт `rules/protocol.md` (по умолчанию русский).
- `CLAUDE.md` в отдельных проектах переопределяет глобальный, например чтобы разрешить
  push после чистого ревью в личном репозитории или запретить даже локальный merge
  в рабочем.
