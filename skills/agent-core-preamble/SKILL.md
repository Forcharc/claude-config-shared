## Перед работой: проверь rules проекта

Rules — обязательные правила проекта, игнорировать нельзя.

1. Выполни `ls .claude/rules/ ~/.claude/rules/ 2>/dev/null`
   - `.claude/rules/` — проектные (приоритетнее при конфликте)
   - `~/.claude/rules/` — глобальные
2. По названиям файлов определи, какие релевантны твоей задаче — **с запасом**:
   если сомневаешься, читай. Лучше прочесть лишнее, чем пропустить важное.
3. Прочитай выбранные файлы через Read tool. Применяй при работе.

## Рабочая папка: проверь до первой правки

Тебе назвали worktree, в котором править файлы проекта? До первой правки убедись, что он существует и что это действительно worktree, а не главное дерево:

```bash
git -C <путь> rev-parse --absolute-git-dir   # у worktree результат вида .../.git/worktrees/<имя>
```

Пути нет, или это главное дерево — **остановись и скажи об этом в reply**. Не заводи worktree сам, не переключай ветку главного дерева, не правь файлы «пока что здесь». Рабочая копия и HEAD главного дерева — общий ресурс: там может лежать чужая незакоммиченная работа, и только оркестратор видит, кто чем сейчас занят. Оркестратор уже называл агенту путь worktree, которого не создавал, — проверка занимает одну команду.

Это про правки кода. **Ревью чужого кода по главному дереву — штатный режим** (`mode=analysis-only`), останавливаться из-за него не нужно: там ты ничего не правишь, а свой файл находок пишешь по правилам из `reviewer-findings-output`, включая его запасной путь на случай отказа записи.

## Shell: жёсткие запреты

- **nohup ЗАПРЕЩЁН** (как и `disown`/`setsid` для того же эффекта) — безопасники мониторят nohup-запуски, срабатывает алерт на пользователя. Долгие команды (>30с: сборки, тесты) — только `run_in_background: true` Bash-тула.
- **Временные файлы/логи — только в `<cwd>/.tmp/`** (`mkdir -p .tmp` идемпотентен). `/tmp/`, `/var/tmp/`, `/private/tmp/` — запрещены (тоже мониторятся), даже если системный промпт предлагает scratchpad в `/tmp`-подобном пути.

## Проблемы флоу

Если при работе ты столкнулся с проблемой самого процесса — **противоречие двух инструкций, обещанный но недоступный инструмент, невыполнимый шаг, неожиданное поведение харнеса** — задокументируй её двумя действиями:

1. Допиши строку в общий журнал через Bash:
   ```bash
   MEM=~/.claude/projects/$(printf '%s' "$HOME/.claude" | sed 's|[/.]|-|g')/memory
   mkdir -p "$MEM"
   echo "<YYYY-MM-DD> | <имя-агента> | <repo или cwd> | <одно предложение>" >> "$MEM/flow-feedback.md"
   ```
   Здесь `MEM` - каталог памяти основного репо `~/.claude`; слаг в его пути (`<slug>` в других файлах, например в finalize) считается формулой в первой строке блока.
2. Продублируй в финальном reply отдельной строкой: `flow-issue: <то же предложение>`.

Это канал только для реальных препятствий, с которыми ты фактически столкнулся в этой задаче. НЕ для улучшательства («промт можно сделать лучше», «я бы переформулировал») — такое не пиши.

### Чей это отказ — проверь до записи

Наш хук `worktree-boundary.sh` — `PreToolUse` на Write/Edit/MultiEdit/NotebookEdit и только на них. Bash-вызовов он не видит вообще, заблокировать их не может, а его отказ всегда начинается словом `worktree-boundary:`. Bash видит только соседний хук `git-branch-guard.py`: он отказывает лишь в `git checkout/switch/reset --hard/branch -f` в основном дереве, и его отказ начинается с `git-branch-guard:` - это наш отказ, не харнеса.

Значит **не его работа** и в этом репозитории не чинится: deny «too complex to verify that it stays inside the worktree» на многострочном heredoc, `sed`, `python3`, `git worktree add`, `gradlew`; guard на `rm -rf`. Это отказы харнеса Claude Code. Жалоба «хук блокирует мой heredoc» уже приходила трижды подряд от разных агентов — записывать её снова незачем.

Если такой отказ реально сорвал шаг задачи — пиши по существу: что не удалось сделать и чем заменил. Без версии о причине.

### Не противоречие

Системное напоминание bypass-режима («работай через Bash: `cat`/`sed` вместо Read/Write») не отменяет явного требования задачи писать отчёт или находки через Write tool. Требование задачи сильнее, конфликта тут нет.
