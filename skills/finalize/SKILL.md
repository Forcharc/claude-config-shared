# Finalize

Закрой все техдолги текущей сессии, разбери flow-feedback и нити сессии.

## Шаг 1: Найти техдолги этой сессии

Собираем кандидатов из двух независимых источников и объединяем — UUID-логика хрупкая (подпись могла уехать под id другой сессии, `unknown` при пустой переменной), worktree-локальный файл — детерминированный fallback.

1. **Worktree-local история** (приоритетный источник). Файл `<git root>/.tmp/active-tds.md`, куда `/techdebt` дописывает id каждого созданного техдолга. `<git root>` — `git rev-parse --show-toplevel`. Прочитай — это список `td-NNN`, созданных в текущем worktree (живёт пока жив worktree, не шарится между ветками).

2. **UUID текущей сессии** — `$CLAUDE_CODE_SESSION_ID`:
   ```bash
   echo "${CLAUDE_CODE_SESSION_ID:-unknown}"
   ```
   Не используй `ls -t ~/.claude/projects/*/*.jsonl`: в форках он вернёт UUID родительской сессии, а при параллельной работе — файл ЧУЖОЙ сессии, если та писала свежее. Пустая переменная — см. `/commit`, секция «Подпись коммита».

   **Совпадение UUID — не доказательство владения.** Прежде чем трогать найденный техдолг, сверь его поле `task:` с тем, чем реально занималась эта сессия. Не сошлось — долг чужой (подписан неверно), не закрывай его и не переписывай: скажи пользователю и оставь владельцу.

3. Путь к tech-debt директории — см. `/techdebt` шаг 0.

4. Собери `td-*.md` файлы, удовлетворяющие любому из условий:
   - id присутствует в `<git root>/.tmp/active-tds.md`, ИЛИ
   - frontmatter `originSessionId` == текущему UUID.

   Записи без `originSessionId`, не упомянутые в active-tds и с другим UUID — не трогай.

Если после всех источников список пуст — доложи пользователю и выйди.

**Список фиксируется здесь и дальше не растёт.** Техдолги, появившиеся уже во время работы скилла (их заводит `review-judge` в шаге 4, ревьюя мои же закрывающие правки), в текущий прогон НЕ берутся и нового прогона не запускают — они ждут следующего `/finalize`. Без этого получается петля: закрыл долг → ревью правки → новый долг → правило шага 10 требует снова закрыть, и так до бесконечности, потому что в документе-инструкции всегда найдётся соседнее место, которое «тоже стоило бы уточнить». Останавливать петлю, уговаривая ревьюеров и судью не искать, — нельзя: так же легко замолчать и настоящий дефект.

## Шаг 2: Показать и триаж

Выведи найденный список. Для спорных техдолгов определи категорию вместе с user'ом; очевидные — категоризируй и чини без участия user'а (критерий ниже), покажи их в общем списке постфактум.

- **Чинить** — нет блокера, решение применимо сейчас.
- **Блокер** — есть реальная зависимость (другая фича, ожидание архитектурного решения, внешнее условие). Не чиним сейчас, но запись остаётся.
- **Неактуально** — стал неактуален (фича отменена, код переписан, проблема решилась сама). Не чиним и не храним.

**Очевидное чини без подтверждения** — когда в записи есть готовое «Предлагаемое решение», правка локальная (несколько строк, один файл) и не противоречит причине, по которой долг отложили: запись могла фиксировать «не чиним сейчас потому-то» (например «не чиним сейчас, чтобы не усложнять миграцию X») — такое решение уважай, не отменяй молча.

Подтверждения жди только для спорного: архитектурные изменения, несколько модулей, намеренно отложенное. Дефолт при молчании user'а — «чинить».

## Шаг 3: Обработать по категориям

**Важно:** шаги 3b и 3c правят файлы напрямую. Убедись что работаешь внутри worktree — если ещё нет, `EnterWorktree` перед началом.

### 3a. «Чинить» — делегировать параллельно

Для каждого техдолга — `implementer` (правила делегирования, worktree-изоляция, передача данных через файлы — см. `rules/workflow.md`). В промпте: путь к `td-NNN-*.md`, задача «применить Предлагаемое решение, удалить сам .md-файл, НЕ трогать INDEX.md (skill обновит INDEX пакетно в Шаге 5)».

### 3b. «Блокер» — пометить и оставить

Для каждого техдолга в этой категории:
1. Открой `td-NNN-*.md` через Read.
2. Добавь в конец секцию `## Блокер` с явным описанием: от чего зависим, почему сейчас не чиним, при каких условиях можно вернуться.
3. В frontmatter поменяй `status: open` → `status: blocked`.
4. Файл остаётся на месте, в INDEX тоже остаётся (строка не убирается в Шаге 5).

### 3c. «Неактуально» — удалить

Для каждого техдолга в этой категории:
1. Удали файл: `rm <путь>/td-NNN-*.md`.
2. Запомни id и slug для Шага 5 (там убирается из INDEX).
3. Отдельный коммит с сообщением вида `Remove stale td-NNN: <slug>` и body — почему стал неактуален (1-2 строки контекста).

Шаг 3c не требует `implementer`'а — это чисто файловая операция, выполняется напрямую (внутри активного worktree).

## Шаг 4: После каждой закрытой пачки (категория «чинить») — `/review`

Коммити правки и вызывай `/review` на HEAD. **Обязательно передавай `repo=<worktree-path>`** — иначе если cwd не совпадает с worktree, /review проверит HEAD основного дерева и fix-коммиты цикла /review уйдут в неправильный ref. Всё остальное в зоне `/review`.

## Шаг 5: Обновление INDEX, потом закрыть worktree

**Порядок важен:** правка INDEX.md — это Write/Edit, хук `worktree-boundary.sh` его пропустит только внутри worktree. Делай эту правку ДО закрытия ветки (merge или PR), пока worktree ещё активен (как и весь шаг 3) — не после, в главном дереве.

Одним коммитом (всё ещё внутри worktree) убери из INDEX.md строки для:
- закрытых техдолгов из категории «чинить»,
- удалённых техдолгов из категории «неактуально».

Строки из категории «блокер» НЕ убираются — они остаются в INDEX с пометкой `status: blocked`.

Дополнительно очисти `<git root>/.tmp/active-tds.md` по проверяемому критерию: **удаляй строку id, только если файла записи `<id>-*.md` больше нет на диске** (id в журнале уже с префиксом: строке `td-NNN` соответствует файл `td-NNN-*.md`) — значит долг закрыт («чинить») или удалён («неактуально»). Файл на месте — строку оставь: это либо «блокер», либо долг, заведённый `review-judge` уже во время этого прогона и отложенный до следующего раза. Критерий по диску намеренно не полагается на память о шаге 1: список мог не пережить compaction, а стереть строку живого техдолга — значит потерять его совсем. Файл целиком не обнуляй; если после этого он пуст — можно удалить.

Когда worktree чист — закрой его по `~/.claude/rules/workflow.md` шаг 11 (там же сказано, merge это или pull request). `git merge` — Bash-операция, не Write/Edit, хуком не блокируется. Push в дефолт-сценарии (слить `main` в origin после локального merge) — по проектному CLAUDE.md: явного разрешения нет — не пушь. В PR-сценарии push ветки отдельного разрешения не требует, его уже дало правило проекта, попросившее PR.

## Шаг 5b: Разобрать flow-feedback

Прочитай `~/.claude/projects/<slug>/memory/flow-feedback.md` (slug - см. раздел «Проблемы флоу» в agent-core-preamble; журнал проблем флоу, который пишут агенты). Если непустой — триаж каждой строки вместе с user'ом: починить промт сейчас (мелочь — прямо здесь же), записать td, или отбросить как шум. Разобранные строки удали из журнала; неразобранные (отложенные user'ом) оставь.

## Шаг 5c: Нити сессии

Собери нерешённые нити текущей сессии из двух источников:

1. **Журнал**: `~/.claude/projects/<slug>/memory/session-threads.md` (slug по main-репо текущего проекта) — строки текущей сессии, фильтр по полному sessionId (UUID) в начале строки. Если по текущему UUID строк нет или мало — проверь UUID родителя (compaction-edge-case: сессия может быть продолжением после compaction, строки могли писаться с родительским UUID; алгоритм поиска родителя — тот же что в шаге 1 пункт 5).
2. **Ретроспектива**: перечитай диалог сессии из своего контекста — отложенные идеи («ИДЕЯ», «потом обсудим»), незакрытые вопросы, данные user'у обещания. Compaction мог вырезать середину диалога — поэтому журнал первичен, ретроспектива дополняет.

Объединяя источники: если нить из ретроспективы совпадает по смыслу со строкой журнала — считай её одной нитью, не дублируй.

Объединённый список покажи user'у и триажь каждую нить вместе с ним: **сделать сейчас** (только мелочь — крупное оформляй отдельной задачей после финализации) / **в память** (backlog-файл проекта) / **в td** (`/techdebt`) / **отбросить**. Дефолт при молчании user'а — «в память».

После триажа: для каждой разобранной нити сначала выполни действие (запись в память / td), потом удали строку из журнала. Чужие строки не трогай.

## Подписи

Все коммиты, создаваемые этим скиллом (3c, шаг 5), подписываются по канонике `/commit` секция «Подпись коммита» (журнал всегда; trailer — только при opt-in проектного CLAUDE.md).

## Шаг 6: Отчёт

Короткий итог пользователю: закрыто X (чинили), помечено блокерами Y, удалено как неактуальные Z, не закрылись W и почему.
